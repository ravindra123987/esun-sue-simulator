XPU A NIC ── hop 1 ── Switch port 1 → port 7 ── hop 2 ── XPU B NIC

Three devices, two 800G cables. Every cable end runs its own link-level retry (LLR) and credit-based flow control (CBFC), so the switch is a receiver on hop 1 and a sender on hop 2. Every frame, control block and state you see is what the simulator did.

How the model maps to the hardware. Each cable end is a MAC with LLR and CBFC (sim/mac.py). XPU A's NIC is the sender on hop 1, with an always-full send queue in HBM. Switch port 1 is hop 1's receiver; the frames it accepts wait in its ingress buffer, whose size is the credit pool it gives XPU A. Switch port 7 is hop 2's sender: it takes a frame out of that buffer when its own LLR window and XPU B's credits allow, which frees XPU A's credits. XPU B's NIC is hop 2's receiver and writes into HBM at a set rate. Control blocks (8 B) ride in fixed slots every 2048 B of link time and are drawn wider than their true 0.08 ns.
Not modelled: switch pipeline latency (0 ns here) and other switch ports, DMA timing out of XPU A's HBM, more than one VC or flow, the PCS-status timer. Recorded runs: tools/make_traces.py; live runs: tools/live.py (local, standard library only); captions: sim/trace.py.
