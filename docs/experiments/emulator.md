# M4: the netns emulator

Real frames instead of simulated ones: `emu/` runs a user-space switch and N SUE-T endpoints as Linux processes on veths in network namespaces, with UEC link-layer retry and credit-based flow control on every link end, and injects faults. The frames are the ones `sue/frame.py` builds and `wireshark/sue.lua` decodes, so a run leaves a pcap per link that Wireshark shows field by field. Everything here is regenerated by `tools/run_m4.py` (about two minutes in the VM); numbers are in [emulator-results.json](emulator-results.json), three trimmed captures are in [pcaps/emu/](../../pcaps/emu/).

> **What this is for.** Packets and behaviour, not timing. The simulator (M2, M3) answers "how many nanoseconds"; the emulator answers "what is on the wire and what does each layer do with it". Its round trip is a few milliseconds of Python, so every timer is a thousand times the simulator's, and no latency or completion number below is comparable with sim/. The *shapes* are: that is what T4-E3 are checked against at the end.

## The lab

```
xpu0 ns: eth0 02:a0:00:00:00:00 ──veth── sw0-p0 02:5f:00:00:00:00 ┐
xpu1 ns: eth0 02:a0:00:00:00:01 ──veth── sw0-p1 02:5f:00:00:00:01 ├ sw0 ns: python -m emu.switch
xpu2 ns: ...                                                       ┘
```

- **Switch** (`emu/switch.py`): one packet socket per port; forwarding by the UFH_16 destination container (the XPU id) or, for ESUN/Ethernet frames, the MAC DA; every port is a full link end (below); frames wait in the ingress port's lossless buffer, which is the credit pool its sender sees, and the egress port takes the oldest frame addressed to it from any ingress buffer (virtual output queueing) when its own LLR window and the next hop's credits allow. Store and forward, no pipeline latency.
- **Link end** (`emu/port.py`): the same layering as `sim/mac.py`, driven by an event loop. LLR (UEC §5.1): 20-bit sequence numbers, a 64 KB replay buffer, ACK/NACK/INIT/INIT_ECHO, the replay timer, FLUSH after 8 replays without progress, then INIT. CBFC (§5.2): credits of 64 B per VC, two VCs (requests on VC 0, ACK packets on VC 1), S_VC_CC counted when a lossless frame is first sent, R_VC_CC only for frames LLR accepted in order, CF_Update as a control unit, CC_Update as the 64 B MAC control frame of Table 5-22. The §5.2.9 rules hold by the same layering as in M2. The INIT handshake runs at start-up, as on a real link.
- **Endpoint** (`emu/endpoint.py`): one queue per peer, stores of 256 B handed over instantly up to a 64 KB transmit buffer, packing up to 8 CMD_PDUs / 2 KB per packet, one RODL PDC per peer over UFH_16 with `syn` on the first packet and the hidden PSN in the UET CRC, a 64-packet window, Go-Back-N on a NACK or the RTO, or SUE-lite (a loss fails what is in flight, the next packet re-establishes the PDC). Operational ACKs: the receiver executes a store at once, holds the ACK 2 ms for a request going the other way to carry (`rev_cack_psn_lsb`), else sends a bare ACK packet; a gap is NACKed once. The receiver recovers a `syn=0` packet's PSN the way the dissector does: expected PSN first, then ±64 around it, by recomputing the CRC.
- **Captures**: `tcpdump` on the switch side of every link, both directions in one file. `emu/analyze.py` counts what is in a pcap; the dissector decodes it.
- **Faults** (`tools/run_m4.py`): bit errors at a set rate on what a port sends (frames and control units alike), lost credit messages (a port drops a fraction of the CF_Updates it receives), a link set down and up on the switch side, a stuck receiver (a NIC stops draining its receive buffer for a while), LLR off, SUE-lite.

### What a veth cannot carry (decision E1)

On a real UE link the LLR sequence number rides in the preamble, and LLR ACK/NACK/INIT and CF_Update are control ordered sets the PCS inserts between or inside frames (§5.1.3, §5.2.6.1); a capture never shows them. A veth has no preamble and no PCS, and a packet socket strips the FCS. The emulator therefore wraps every link-layer unit in a frame of EtherType 0x88B6 (IEEE local experimental) with an 8 B shim: the CtlOS message type as UEC Table 5-8 numbers it (0x00 = a frame follows, 0x01 LLR_ACK, 0x02 LLR_NACK, 0x03 LLR_INIT, 0x04 LLR_INIT_ECHO, 0x10 CF_Update), the 20-bit sequence number, and a CRC-32 of the inner frame standing in for the FCS; a control unit carries the six data bytes D2..D7 exactly as Tables 5-8 and 5-21 lay them out, a frame carries the UFH_16 frame unchanged. `sue.lua` decodes the shim (`sue.llr.*`, `sue.cbfc.*`), hands the inner frame to the UFH_16 / Ethernet dissectors, and decodes CC_Update. The point is to make the link layer visible in Wireshark, which real NICs never allow; it is not a protocol proposal. (`emu/shim.py`)

### Decisions you can overturn

| # | Choice | What we do | The alternative | Where |
|---|---|---|---|---|
| E1 | Link layer on a veth | The 0x88B6 shim above | Hide LLR entirely (sequence numbers in a side channel): captures would then look like a real NIC's, and show nothing of the link layer | `emu/shim.py` |
| E2 | Timers | Replay timer 50 ms, 8 retries, RTO 1 s (> 50 ms × 9, the rule from M3 T4), ACK hold 2 ms, CtlOS slot 1 ms, INIT every 10 ms, CF_min 0.2 ms, CF_max 5 ms, CC_Update every 20 ms | Anything that keeps the ordering; the first run used the simulator's ratios and a 5 ms replay timer, and a clean link produced replays and flushes (see below) | `PortCfg`, `Endpoint` |
| E3 | CtlOS cadence | An LLR_ACK after 2 KB or 8 frames received, or at the 1 ms slot; a NACK at once; CF_Update when credits were freed and 0.2 ms passed | Strict byte spacing as the PCS does it | `Port._ctlos_opportunity` |
| E4 | Line rate | None: a port transmits in bursts of 8 frames per loop pass, bounded by the LLR window and credits | A token bucket per port, for a rate | `PortCfg.burst` |
| E5 | PDC identity | PDC id = the peer's XPU id on both sides; first PSN 1000 × (xpu + 1); PSN recovery window ±64 | Allocated ids with a handshake; random initial PSN | `Endpoint` |
| E6 | Scope | Stores only, operational ACKs only, UFH_16 only on the endpoints (the switch forwards ESUN frames by DA), the XPU interface instant | Loads, delivery ACKs and ESUN framing as in `sim/suet.py` | `Endpoint` |
| E7 | Faults | BER applied per bit to what a port sends, control units included; lost CF_Updates as a receive-side drop fraction; link down on the switch side; stuck receiver = NIC buffer not drained | tc netem on the veths (corrupts the shim as well, which LLR would not see) | `Port`, `Lab.link` |
| E8 | Kernel path | SO_RCVBUFFORCE 64 MB on the packet sockets, `netdev_max_backlog` raised | Leave defaults: the 208 KB socket buffer overflows under an LLR replay burst, which a real link cannot do | `emu/port.py raw_socket`, `Lab.build` |
| E9 | Out-of-order on UFH_16 (four-plane runs) | Sprayed traffic keeps the RODL frame layout and is accepted out of order; an ACK names the packet it answers in ack_psn; syn packets carry psn_offset and stay syn until the first ACK; probes are ACK frames with flag 0x40, answered with 0x20 | UFH_16 defines only RODL and ACK formats; real RUD/ROD would use the general PDS header (not built yet) | `emu/endpoint.py` |
| E10 | Four-plane timing | Window 8 packets per PDC (a PSN span, not a count), LLR replay timer 200 ms (gives up after 1.8 s), transport timer 4 s with LLR, 1 s without, probes every 1 s | The single-plane values: with four ports per Python process, frames queue for longer than a 50 ms replay timer and a 64-packet window only adds queueing | `tools/run_m4.py` `REPLAY`, `WINDOW`, `PDESIGNS` |
| E11 | Start of a run | Every XPU opens its sockets, then all start sending together (a go file); fault times count from then | Start as soon as each process is up: without LLR's INIT handshake the first packet can reach a peer that is not listening yet, and is lost | `Lab`, `--go-file` |

## The runs

Four XPUs, all-to-all, 32 KB to each peer as 256 B stores (eight runs; 256 KB per peer for the outage and stuck-receiver runs, which need traffic in flight when the fault hits). Faults on link 1 (XPU 1 ⇄ switch port 1). Bit error rate 1e-5 per bit, as in T4: a 2.1 KB frame is corrupted with probability 16 %.

**What each run shows.**

- **ber-llr**: 41 corrupted frames on link 1 cost 12 LLR NACKs and 273 replayed frames (a replay resends the whole buffer, so several frames per error, as M2 E3 measured), 2 timer replays where the NACK or the replay's first frame was itself hit, and **nothing at the transport**: no gap, no NACK, no retransmission, every store done. Completion 0.14 s against 0.06 s clean.
- **ber-nollr**: the same errors become RODL gaps (107), NACKs (10), Go-Back-N retransmissions (138) and, where no later packet was there to trigger a NACK, RTOs (4 × 1 s). Completion 1.07 s. And 1054 credits reclaimed by CC_Update: every corrupted frame had consumed credits at the sender that the receiver never counted, which is exactly the leak §5.2.5.4 gives CC_Update to repair.
- **ber-lite**: with no retransmission a loss closes the PDC; 520 of 1536 stores failed and 6 PDCs were re-established with `syn`. The survivors kept the clean latency.
- **lost-cf**: 365 CF_Updates dropped, no visible effect: CF_Update is cumulative and CF_max (5 ms here) resends it. Completion and stalls are those of the clean run.
- **stuck-rx**: XPU 1's buffer stops draining, so its CF_Updates stop, switch port 1 runs out of credits toward it, its ingress buffers fill, and the three senders stall (1666 credit stalls) until the XPU resumes. **Zero overflows, zero drops**: CBFC did its job.
- **link-flap** (0.2 s): the switch's sends fail while the link is down (364 send errors on port 1), the replay timer fires until the link is back (6 timer replays, 313 frames), and LLR delivers everything in order: **no transport retransmission**. The sim's `outage-short` scenario, in real packets.
- **link-outage** (1.0 s): 8 replays without progress and port 1 flushes (so does XPU 1's NIC), re-initialises, and the frames in the buffers are lost: RODL sees 154 gaps, NACKs 4 times and retransmits 184 packets; CC_Update reclaims 1022 credits for the flushed frames. Completion 2.0 s. The sim's `outage-flush`.

### Packets per second (the AF_PACKET question)

One XPU sends 4 MB (2048 packets of eight 256 B stores) to another through the switch, no capture:

| | |
|---|---|
| End-to-end | 410 packets/s, 16 400 stores/s |
| Endpoint send path (pack 8 SES headers, UFH_16 header, CRC32C) | 0.46 ms per packet, measured on the Mac |
| Endpoint receive path (Scapy parse 0.17 ms + CRC32C 0.11 ms) | 0.28 ms per packet |
| Switch forward (zlib CRC-32 on the shim, table lookup) | well under 0.1 ms per frame |
| Credit stalls at the sender | 2001 |

The packet socket is not the limit; the Python endpoints are, and most of the sender's time is spent waiting for credits that come back at the CtlOS cadence from a receiver that parses and verifies each packet in pure Python. AF_XDP would move the kernel copy, which is not where the time goes; an endpoint data path in C or Rust would. For the purpose of this emulator (behaviour and captures, a few thousand packets per scenario) AF_PACKET is enough, which answers the open question in plan.md.

### What the first run taught (and why E2, E4 and E8 exist)

The first clean run had 50 RODL retransmissions per XPU and the switch ports flushed. Nothing was wrong with the protocols: an endpoint sent its whole 64 KB LLR window in one burst, about 15 ms of CRC work during which it read nothing from its socket, so it could not acknowledge the switch's frames inside the 5 ms replay timer inherited from the simulator's ratios; the switch replayed the window, the replays overflowed the 208 KB socket buffer the kernel allows by default, the overflow looked like loss, and the LLR state machines did exactly what the spec says they should do about it. Three emulator facts had to be made explicit: a port transmits in bounded bursts and the loop reads between them (E4), timers follow the emulator's round trip, not the simulator's (E2), and the kernel path between veth and process must be deep enough never to drop what a real link would not (E8). The simulator's rule from T4 reappeared unchanged: the transport timer must exceed the link layer's worst-case recovery.

## Against the simulator

The point of M4 was to check that the emulator reproduces the simulator's failure behaviour qualitatively. Side by side:

| Fault | Simulator (M2 / M3) | Emulator | Same shape? |
|---|---|---|---|
| Bit errors, LLR on | E3, T4: loss repaired in one link round trip, the transport sees nothing; ~14 frames replayed per error | ber-llr: 0 RODL events, 273 replays for 41 errors | yes |
| Bit errors, LLR off | T4: RODL NACK + Go-Back-N, the tail is the RTO | ber-nollr: 138 retransmissions, 4 RTOs, completion set by the 1 s RTO | yes |
| Bit errors, SUE-lite | T4: survivors keep clean latency, the rest fail | ber-lite: 520 failed, PDCs re-established | yes |
| Lost credit messages | E4 (rule 4 / CF_max) | lost-cf: no effect at 70 % loss | yes |
| Slow or stuck receiver | backpressure / small-pool viewer scenarios: stalls move back hop by hop, no drops | stuck-rx: 1666 stalls, 0 overflows | yes |
| Short outage | outage-short: LLR absorbs it | link-flap: 6 timer replays, 0 RODL events | yes |
| Long outage | outage-flush: FLUSH, INIT, transport recovers what was flushed; CC_Update reclaims | link-outage: 2 flushes, 184 RODL retransmissions, 1022 credits reclaimed | yes |
| Credit leak repair | E4 rule 1–3: CC_Update reclaims credits of frames the receiver never counted | ber-nollr 1054, ber-lite 442, link-outage 1022 credits reclaimed | yes |

One thing the emulator shows that the simulator does not: what the state machines do when the *implementation* is slow. Every timer in UEC §5.1 is a guess about the peer's speed, and a peer that answers late is indistinguishable from a lost ACK.

## Reading a capture

```
tshark -X lua_script:wireshark/sue.lua -r pcaps/emu/ber-llr-link1.pcap
```

shows LLR_INIT / INIT_ECHO first, then `SUE/UFH16 ... LLR seq 0  RODL SYN PSN 2000 ... WRITE 256B ×8 ... CRC Good`, LLR_ACK units with their `ack_nack_seq`, CF_Update units with both VCs' R_VC_CF, CC_Update frames with sixteen S_VC_CC values, and on the faulted link frames flagged `[corrupted frame]` by the shim CRC, the LLR_NACK that follows, and the replayed frames, which the dissector's per-PDC PSN tracker reports as `[back N]` because it sees the same PSN again. Filter `sue.llr.type == 2` for NACKs, `sue.llr.crc.status == 1` for corrupted frames, `sue.pds.rodl.psn_gap < 0` for replays.

## Assumptions

Printed here because there is no figure to print them on: the shim of E1; the timers of E2; no line rate (E4); the 64 KB LLR replay buffer and 1024-sequence window, 1024 credits of 64 B per VC at every port, two VCs; stores of 256 B, 32 KB (or 256 KB) per peer, packing to 8; four XPUs, one plane; the switch adds no latency; faults on link 1 only; one run per scenario (no seeds: the run-to-run spread comes from the OS scheduler, and the counts above move by tens of percent between runs while the zeros stay zero).

## How to run it

The lab needs root on Linux. On the Mac it runs in the Lima VM `clab`, with the repo on the read-only home mount and a venv with scapy in the VM:

```
limactl shell clab
python3 -m venv ~/esun-venv && ~/esun-venv/bin/pip install scapy==2.6.1
cd /Users/<you>/ws/personal/esun-sue-simulator
sudo env PYTHONPATH=$PWD PYTHONDONTWRITEBYTECODE=1 EMU_PYTHON=$HOME/esun-venv/bin/python \
    $HOME/esun-venv/bin/python tools/run_m4.py run --out $HOME/emu-out        # ~2 min, all scenarios
# back on the Mac
limactl copy -r clab:~/emu-out /tmp/emu-out
.venv/bin/python tools/run_m4.py report /tmp/emu-out                          # tables + emulator-results.json
```

A single run: `sudo ... python -m emu.lab --n 4 --out ~/emu-out/x --endpoint-args "--bytes-per-peer 65536 --no-llr"`. `tests/test_emu.py` exercises the link layer and the endpoint over an in-memory wire without namespaces; `tests/test_emu_pcap.py` runs the dissector over the sample captures.

The first captures of this milestone were taken with tcpdump buffering whole blocks of the kernel's capture ring, so a short run could end before its last block reached the file: the clean run's link-1 capture held 52 of the 70 frames the switch sent. `emu/lab.py` now captures in immediate mode; the tables above, the samples in `pcaps/emu/` and [emulator-results.json](emulator-results.json) come from a run with that fix and with the four-plane changes to the lab (start barrier E11, 32 frames per socket per pass). ## Four planes (M5b)

The lab also builds several planes (`emu.lab.run(planes=4)`, `tools/run_m4.py run --planes`): one switch namespace and process per plane, one veth per XPU per plane, and endpoints with a port per plane and the three path policies of the simulator (pinned, failover, spray with out-of-order delivery). The results and how they compare with the simulator are in [docs/where-should-retry-live.md](../where-should-retry-live.md#the-same-faults-on-real-frames-emulator); the raw numbers in [emulator-planes-results.json](emulator-planes-results.json). Getting the four-plane runs clean took three of the decisions above: E10 (a Python process serving four ports needs longer timers and a shorter window), E11 (start every XPU together, or a sender without LLR's INIT handshake can lose its first packet to a peer that is not listening yet), and the window rule M5-13 (bound the PSN span in flight, not the packet count).
